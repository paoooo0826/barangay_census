# Scan fixes — 6 October 2026

The census API now requires new submissions to include owned, non-empty ID front/back and live-photo Storage objects. Failed/skipped live evidence and missing files are rejected. Direct resident inserts and direct verification-evidence writes are blocked so they cannot bypass the atomic save API. The public API signature remains unchanged; the privileged implementation lives in the private schema.

This is evidence validation, not server-side biometric attestation. Face matching and liveness are performed in the browser. Auto-approval remains the requested administrative workflow; admins can inspect and reject records. Existing records are not retroactively reclassified or deleted. Ordinary edits leave their original evidence unchanged, including legacy skipped-verification records.

Auth initialization and account changes wait for the correct profile. Token refresh and repeated sign-in events for the same user preserve mounted pages and unfinished Census Form edits. Stale profile/session responses cannot restore access after logout.

Resident Records, admin Appointments/Services/History, and Announcements use server filtering, sorting, exact counts, and bounded page queries. Dashboard counts/recent-five records and the four charts come from aggregate queries. The boarding-house owner selector searches up to 20 matches instead of downloading the full resident list. Announcement images are signed only for the visible page. Pagination clamps both data and controls after a list shrinks.

Analytics counts approved census records only and explains excluded statuses. It does not label all submissions as the current population. Residence start dates remain unknown until genuine dates are entered; no registration timestamps are substituted.

The legacy direct-update trigger now gets only the authenticated account's email through a restricted helper instead of trying to read auth.users as the client role. Resident edits still cannot change approval status, ownership, tracking number, or original submission dates.

Dependency overrides patch brace-expansion, baseline-browser-mapping, browserslist, source-map-js, and postcss-selector-parser. Tailwind stays on version 3.4.19. Supabase JS is pinned. The braces advisory GHSA-vfj7-8cjw-p6xm has no upstream patched release as of this update. An idempotent install-time nesting guard mitigates its recursive AST walkers and parser, with tests for normal patterns and malicious deep input. npm audit still reports five propagated development dependency alerts from this single unpatched upstream dependency. Production dependencies report zero alerts. Do not use --ignore-scripts: it skips the mitigation. Remove/review the guard when a patched upstream braces release becomes available.

## Migration

Apply the new census_verification_and_admin_paging migration before deploying the updated frontend. It preserves all resident/account/appointment/announcement rows. The previous frontend can still submit validated new registrations; use the updated Census Form for ordinary edits of legacy skipped-verification records.

The connected Supabase project has migration version 20261006045422 applied. All three transactional database checks passed again afterward. Counts remain 12 accounts, 6 residents, 12 appointments, and 4 announcements; the resident row fingerprint is unchanged.

Supabase still reports its existing leaked-password-protection setting as disabled and warns about intentionally exposed privileged API functions. Those notices do not establish that every function is vulnerable. Account/ownership validation is covered by the SQL checks; this update does not claim that browser biometric results are independently verified on the server. The rate-limit table intentionally has no client RLS policies.
